Where we left off, where we're going

Roadmap for today

We've already covered the core ideas of information security: the CIA triad, threat actors, risk, and why we defend systems in the first place. What's been missing is the terrain those threats actually operate on — the network. You cannot reason about a man-in-the-middle attack without knowing what "the middle" is, and you cannot reason about DNS spoofing without knowing what a normal DNS lookup looks like.

So today is a fast, technical recap: how two machines actually exchange data, structured around the journey a single request takes from your browser to a server and back. Every diagram below is click-through — step through it at your own pace.

Today's arc
TCP/IP model → encapsulation → client–server model → a packet's physical journey → the protocols that make it work (DHCP, IP, DNS) → URLs → where attackers actually sit in this picture.
Recap · the stack

The TCP/IP model

Real-world networks are built and taught using the four-layer TCP/IP model (a practical cousin of the seven-layer OSI model). Each layer has one job and only talks to the layers directly above and below it. Click a layer to expand it.

OSI 3 ▸

EthernetWi-Fi (802.11)MAC addressing
Why security cares about layers
Attacks target specific layers. ARP spoofing lives at the network access layer, IP spoofing at the internet layer, SYN floods at the transport layer, and phishing or injection at the application layer. Knowing the layer tells you which defence belongs where.
Recap · how data actually travels

Encapsulation: wrapping data layer by layer

Data doesn't leave your machine as raw application content. Each layer of the stack wraps the layer above it in its own header (like nesting envelopes inside envelopes), and the receiving machine unwraps them in reverse order — a process called decapsulation. Step through the build-up below.

Frame header + trailer — network access layer
IP header — internet layer (source/destination IP)
TCP header — transport layer (source/destination port, sequence #)
Application data "GET /login HTTP/1.1"

At each hop, the sizes have names too: data → segment (with TCP header) → packet (with IP header) → frame (with link header/trailer) → bits on the physical medium.

Recap · the architecture underneath every app

Client–server architecture

Almost everything you use online follows the same shape: a client (your browser, your phone app) initiates a request, and a server (a machine that's always listening, usually 24/7) processes it and replies. The client never talks directly to "the internet" — it talks to a specific server, at a specific IP address, on a specific port.

Where trust breaks down
The client has to trust that the server it reached really is the server it asked for, and the server has to trust that the request really came from that client. Both assumptions are exactly what spoofing, DNS poisoning, and session hijacking attack — all covered later in this module.

Recap · addressing

IP addressing, in brief

An IPv4 address is a 32-bit number written as four decimal octets, e.g. 192.168.1.45. It splits into a network portion and a host portion, defined by a subnet mask — this is how a router knows whether a destination is on the local network or needs to be forwarded outward. IPv6 exists because IPv4's roughly 4.3 billion addresses ran out; it uses 128 bits, written in hexadecimal groups like 2001:0db8:85a3::8a2e:0370:7334.

A second distinction matters constantly in security work:

TypeExample rangeMeaning
Private10.0.0.0/8, 192.168.0.0/16Only valid inside a local network; not routable on the open internet. Your laptop's Wi-Fi address is almost certainly one of these.
Publiceverything elseGlobally unique and routable — this is the address the outside world sees, usually assigned to your router by your ISP.
Why this matters later
Firewalls, VPNs, and NAT (network address translation) all exist because of this public/private split. When you scan a target's exposed surface in a later module, you're really asking: which of their addresses are public, and what's listening there?
Recap · how a device gets online

DHCP: getting an address automatically

When your laptop joins a Wi-Fi network, it doesn't already have an IP address — it has to ask for one. The Dynamic Host Configuration Protocol hands this out automatically using a four-step exchange, remembered by the acronym DORA. Reveal each step.

1 · DISCOVER (client → broadcast)"Is any DHCP server out there? I just joined this network and I need an IP address."
2 · OFFER (server → client)"I can offer you 192.168.1.45, subnet mask 255.255.255.0, for a 24-hour lease."
3 · REQUEST (client → broadcast)"Thanks — I'd like to formally request 192.168.1.45, the address you offered me."
4 · ACKNOWLEDGE (server → client)"Confirmed. 192.168.1.45 is yours, along with your gateway and DNS server addresses."
A well-known abuse of this trust
Because DISCOVER and REQUEST are broadcast to anyone listening, an attacker running a rogue DHCP server on the same network can race the real one and hand out a lease that quietly points your DNS or gateway at a machine they control — a classic setup for a man-in-the-middle position.
Recap · turning names into addresses

DNS: the internet's phonebook

Machines route by IP address, but humans type names like example.com. The Domain Name System resolves one into the other through a chain of servers, none of which know the full answer alone. Step through a typical lookup.

Your browser → recursive resolver"What's the IP address for www.example.com?"
Resolver → root server"I don't know it either — resolver asks a root server: which server handles the .com domain?"
Root server → resolver"I don't have the address, but ask this .com TLD server."
Resolver → TLD server → resolver"Ask the authoritative name server for example.com — here's its address."
Resolver → authoritative server"What's the A record for www.example.com?" → "It's 93.184.216.34."
Resolver → your browser"Here's the address: 93.184.216.34 — and I'll cache it so the next lookup is instant."
Why this chain is a favourite target
DNS replies were designed with no built-in way to verify the responder is who it claims to be. DNS spoofing / cache poisoning exploits exactly that gap — feeding a resolver a forged answer so it caches the wrong IP and quietly redirects everyone. DNSSEC, covered later, is the cryptographic fix.

Where the plaintext problem lives

Bridging into cryptography

Notice something about everything you just walked through: the HTTP request, the DHCP conversation, the DNS lookup — none of it is secret by default. A packet crossing the network access layer is, physically, a signal anyone with access to that link can capture. This is the entire premise the next module is built on.

What you saw todayWhat can go wrongWhat fixes it (coming up)
HTTP request/responseReadable in transit — credentials, cookies, content all exposed to anyone on the path.TLS / HTTPS
DNS lookupUnauthenticated responses can be forged (spoofing, cache poisoning).DNSSEC, DNS-over-HTTPS
DHCP exchangeBroadcast and unauthenticated — a rogue server can hijack it.Port security, DHCP snooping
IP packetSource address can be forged (IP spoofing).Ingress filtering, IPsec
ARP mappingNo authentication of who claims which IP (ARP spoofing).Dynamic ARP inspection, static entries

Every one of these fixes is, at its core, a way of adding confidentiality, integrity, or authenticity to a channel that has none by default — which is precisely what cryptography gives you. That's next week.

Checkpoint quiz

Five quick questions before we move on. Pick an answer for each, then check.

1. Which layer of the TCP/IP model is responsible for routing a packet between networks using IP addresses?

Correct — the internet layer handles IP addressing and routing.
Not quite — that's the internet layer's job (IP addressing and routing).

2. In the DHCP DORA process, what does the client send first?

Correct — DISCOVER is a broadcast, since the client doesn't yet know a DHCP server's address.
Not quite — the client starts with a broadcast DISCOVER message.

3. Which server in a DNS lookup actually holds the real IP address for a specific domain?

Correct — the authoritative server holds the actual DNS records for that domain.
Not quite — that's the authoritative name server's role.

4. In the URL https://www.example.com:443/account?tab=security, what is "tab=security"?

Correct — it's a query parameter, passing extra data to the page.
Not quite — "tab=security" is a query parameter.

5. Why is plain HTTP considered a security risk on its own?

Correct — with no encryption, anyone intercepting the traffic can read it directly.
Not quite — the core issue is that HTTP sends everything unencrypted.
Before you go

Summary

Today's session re-established the network layer as the terrain of information security: the four-layer TCP/IP model, how data is encapsulated on the way out and decapsulated on the way in, the client–server relationship underneath every app you use, and the physical hops a packet takes across switches, routers, and the backbone. We then walked through the protocols that make that journey possible — DHCP getting you online, IP addressing you, DNS naming everything, and the URL as the human-readable interface to all of it.

The thread running through every one of these mechanisms is the same: none of them were designed with an adversary in mind. Next session, we start fixing that with cryptography — building confidentiality, integrity, and authenticity into a stack that, as you've just seen, has none of it by default.
